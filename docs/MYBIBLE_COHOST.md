# استضافة الكتاب المقدس (mybible) داخل أوسكار ديفز — co-host

> سجلّ دائم للمشروع ده. اقراه قبل أي شغل يخصّ `mybible.oscardevs.com`.

## الفكرة
موقع الكتاب المقدس (`mybible.oscardevs.com` — «الكتاب المقدس رفيقي»، فيه **~700 عضو
في درس كتاب مار مرقس**) كان نشر Replit مستقل. بننقله يشتغل على **نفس Reserved VM
بتاع أوسكار ديفز** لتوفير تكلفة النشر التاني — **من غير أي تغيير يحسّه المستخدم.**

## المعمارية (co-host = توجيه، مش دمج/إعادة كتابة)
- **البوّاب:** `src/lib/host_gateway.js` — reverse-proxy: أي طلب لـ`mybible.oscardevs.com`
  (و`mybible2.oscardevs.com`) يتوجّه لتطبيق الكتاب المقدس اللي شغّال كعملية مستقلة
  على بورت داخلي (5001) على نفس الـVM. بيمرّر الـHost الحقيقي فالكوكيز تفضل مربوطة
  بالدومين. **مطفي افتراضياً** لحد ما `MYBIBLE_UPSTREAM` يتحطّ.
- **التشغيل التلقائي:** `server.js` (بعد `app.listen`) بيشغّل `mybible/dist/index.cjs`
  كعملية ابنة لما `MYBIBLE_UPSTREAM` + `MYBIBLE_DATABASE_URL` مضبوطين — بمتغيّرات
  الكتاب المقدس الخاصة. فأمر الـRun يفضل `node server.js`.
- **السورس:** متنسخ في `mybible/` (بيته الجديد). البناء: `cd mybible && npm install && npm run build`
  → `mybible/dist/index.cjs` + `dist/public`. (node_modules/dist مُتجاهَلين في git.)
- نفس نمط `mykid`/`adhd` (توجيه بالدومين قبل middleware أوسكار ديفز).

## المتغيّرات (Secrets على نشر أوسكار ديفز)
| المتغيّر | القيمة | ملاحظة |
|---|---|---|
| `MYBIBLE_UPSTREAM` | `http://127.0.0.1:5001` | بيشغّل البوّاب |
| `MYBIBLE_DATABASE_URL` | رابط Neon بتاع الكتاب المقدس | نفس القاعدة الحالية |
| `MYBIBLE_SESSION_SECRET` | **سرّ الكتاب المقدس نفسه** (مش بتاع أوسكار ديفز!) | لو غلط → الـ700 يتسجّل خروجهم |
| `MYBIBLE_VAPID_PUBLIC_KEY`/`_PRIVATE_KEY` | **مفاتيح VAPID بتاعت الكتاب المقدس نفسه** | **مطلوب لو عايز الإشعارات تفضل شغّالة للـ700** — لو غلط/فاضي، اشتراكاتهم القديمة الإشعار ليها يفشل. **متستخدمش مفاتيح أوسكار ديفز.** |
| `MYBIBLE_DATABASE_TARGET` | فارغ افتراضيًا، أو `ads-supabase` بعد الترحيل | عند تفعيله يستخدم `ADS_DATABASE_URL` مع schema معزول اسمه `mybible` |
| `MYBIBLE_MAINTENANCE_MODE` | `true` أثناء اللقطة النهائية فقط | يعرض 503 ويمنع تشغيل child process، لأن حتى GET قد يكتب session/user |
| `MYBIBLE_SESSION_SECRET_SHA256` | fingerprint للقيمة القديمة قبل النقل | يمنع تشغيل Supabase لو Session secret اتغيرت حتى لو القيمة الجديدة غير فارغة |
| `MYBIBLE_VAPID_PUBLIC_KEY_SHA256` | fingerprint للمفتاح العام القديم قبل النقل | يمنع تشغيل Supabase لو هوية Push اتغيرت، ويتحقق أيضًا أن المفتاح الخاص يطابقه |

Build command: `npm install && (cd mybible && npm install && npm run build)`

## قواعد مقدّسة (متكسرهاش)
- 🚫 **ممنوع أي إعلانات على الكتاب المقدس — نهائياً.** قرار المالك (2026-08-03):
  «مش عايز إعلانات على الكتاب المقدس، ده مجاناً بالكامل». يعني **لا AdSense،
  ولا `ads.txt`، ولا أي وحدة إعلانية** — لا على صفحات القراءة ولا على المحتوى
  الأصلي (التأملات/السنكسار/المشورة). متقترحهاش تاني ولا تنفّذها تحت أي مبرّر
  (ولا حتى «الترافيك هيساعد قبول أدسنس»). تحسين AdSense شغله على `oscardevs.com` بس.
- **نفس الدومين + نفس قاعدة Neon + نفس SESSION_SECRET** → الأعضاء مايحسّوش بحاجة.
- **قاعدة البيانات على Neon (منفصلة عن Replit).** القرار الحالي: **نسيب قاعدة Replit
  زي ما هي، ونأجّل النقل لـNeon مستقل** (تجنّباً للّخبطة). التكلفة ~$26 دلوقتي
  (VM $20 + حوسبة قاعدة الكتاب المقدس ~$6). النقل لـNeon مجاني لاحقاً يوصّلها ~$20.
- **متمسحش مشروع mybible Replit القديم أبداً** — هو ماسك قاعدة Neon (Replit منشئها،
  فمرتبطة بيه). سيبه، وقّف نشره بس. (اسم مقترح: `DB-KEEP-DO-NOT-DELETE`.)
- **الكتاب المقدس بيحتفظ بلوجوه/هويته بالكامل** (البوّاب بيمرّر أصوله: favicon،
  manifest، apple-touch-icon، OG) — صفر لوجو أوسكار ديفز. (اتأكّد عملياً.)
- التفسير (تفاسير المزامير CSV ~103م) **ملفات ثابتة في `mybible/client/public/`**،
  **مش في قاعدة البيانات**. القاعدة نفسها ~76 ميجا (تدخل Neon المجاني بسهولة).

## الأسفار القانونية الثانية (٢٠٢٦-٠٨-٢٧)

نص الكتاب في القاعدة جاي من `api.getbible.net/v2/arabicsv.json` (فان دايك) —
**٦٦ سفر بس**، فالأسفار القانونية الثانية مش موجودة أصلاً. والكنيسة القبطية
بتعتبرها قانونية، فغيابها نقص مش اختيار.

**اتعمل:** `server/deutero.ts` + راوتين + مجلد `data/deutero/`.

- `GET /api/deutero/status` — إيه الموجود فعلاً في القاعدة (بلا مفتاح، قراءة).
- `POST /api/deutero/import?file=<اسم>.json` — بمفتاح `MYBIBLE_SEED_KEY`.

**⚠️ الكود مافيهوش ولا آية.** النص بيتقرا من ملفات JSON، وكل ملف **لازم**
يقول `source` وإلا الاستيراد بيرفضه. الحارس `check-mybible-deutero` بيقع لو
حد كتب نص عربي طويل في `deutero.ts`.

**⚠️ `testament: 'old'` عن قصد:** الواجهة بتجيب `/books/old` و`/books/new`
بس (`client/src/lib/api.ts`) — فأي تصنيف تالت معناه سفر متخزّن صح و**مش
ظاهر خالص**. ده على الأرجح تفسير «فيه إصحاح موجود والموقع مش وارّيه»،
والاستيراد بيصحّح التصنيف الغلط بدل ما يضيف نسخة تانية.

**⚠️ يتشغّل من الموقع الحي مش من شيل Replit** — الشيل بيوصل لقاعدة تانية
(المزلق رقم ١ في `HANDOVER.md`).

**✅ المصدر اتحدّد (٢٠٢٦-٠٨-٢٧):** فحص خارجي لسانت تكلا لقى النص الحرفي:
«والنص التالي هو ترجمة ڤان دايك **(فيما عدا نص الأسفار القانونية الثانية
من الترجمة اليسوعية القديمة 1877 م.)**».

**الترجمة اليسوعية القديمة ١٨٧٧ — والسؤال ده بيحسم الترخيص:** ترجمة من
١٨٧٧ ملكية عامة بلا خلاف (القانون المصري ٨٢/٢٠٠٢: الحياة + ٥٠ سنة؛ أقصى
حماية عالمياً + ٧٠). سانت تكلا **مستضيفين** النص مش مالكينه، وشروطهم
بتتكلم عن **مقالاتهم** لا عن ترجمة عمرها ١٤٨ سنة.

⚠️ **بس ده مش رأي قانوني** — يتراجع مع محامٍ قبل أي اعتماد نهائي.

⛔ **ومفيش سحب من سانت تكلا في كل الأحوال.** `robots.txt` بتاعهم بيحجب
أدوات التحميل بالاسم (Wget · HTTrack · WebCopier · WebZip · archive.org)،
وصفحتهم بتقول «نقل محتوى كامل بعشرات الصفحات أمر غير مُستحَب»، والتواصل
عندهم **متوقف** («التواصل متوقف حاليًا! صلواتكم»). ومش محتاجينه أصلاً —
اليسوعية ١٨٧٧ ملك عام ومتاحة من أي نسخة.

**الخطوة الجاية: مقارنة مش نسخ.** نص مستودع `aymhenry/Bible-for-Windows`
اللي ريبليت شغّال عليه **غالباً هو نفسه اليسوعية ١٨٧٧**. نقارن كام آية —
لو طابقوا، عرفنا مصدر GitHub واستوردنا منه بمصدر معروف.

⚠️ **وتنبيه باقي:** ترويسة `apocrypha-content.ts` بتنسب النص لفان دايك،
**وده مستحيل** (فان دايك استبعدت الأسفار دي). المرشّح الأرجح إنه اليسوعية
١٨٧٧ زي سانت تكلا — بس **ده فرض يتأكّد بالمقارنة مش يتكتب**.

## نقل قاعدة MyBible إلى مشروع Supabase المشترك

MyBible وAds يشتركان في نفس PostgreSQL فقط على مستوى المشروع. جداول MyBible
تبقى داخل schema مستقل اسمه `mybible`؛ ممنوع استعادتها داخل `public` لأن اسم
`push_subscriptions` يتعارض مع Ads.

الـcutover الآمن:

1. خذ dump كاملًا من Neon وbackup مستقلًا من Supabase قبل أي كتابة.
2. استعد dump داخل schema تجريبي، ثم قارن pre-data/data/post-data مع لقطة
   المصدر بعد توحيد اسم الـschema فقط خارج COPY payload.
3. اختبر bundle الإنتاج مع `search_path=mybible_runtime_test,pg_catalog`.
4. انشر مع `MYBIBLE_MAINTENANCE_MODE=true`. البوابة تعرض 503 وMyBible child
   لا يبدأ، لذلك تتوقف session writes والـcron.
5. بعد التأكد أن الموقع في الصيانة، فعّل
   `default_transaction_read_only=on` لدور Neon المستخدم، وأنهِ اتصالاته
   القديمة، ثم تأكد من اتصال جديد أن القيمة `on`. ده fence لقاعدة المصدر:
   أي نشر قديم أو cron بنفس الرابط يفشل في الكتابة بدل ما يسبق اللقطة.
6. خذ dump نهائيًا من Neon واستعده في schema `mybible` داخل transaction واحدة.
7. تحقق من تطابق schema/data/constraints والـsequences. شغّل أيضًا بوابة
   درس مارمرقس قبل فتح الموقع:
   `MYBIBLE_COMPARE_TARGET_SCHEMA=mybible npm run mybible:migration:verify-group`.
   يجب أن تعطي `ok: true`؛ الفحص يشمل الأعضاء والسجلات والتكليفات وتقدم
   القراءة وكل `users` و`sessions` واشتراكات Push. أي فرق يمنع الـcutover.
8. بعد نجاح الفحص، اضبط
   `MYBIBLE_DATABASE_TARGET=ads-supabase` وأزل maintenance mode وأعد النشر.
   الاتصال يستخدم `search_path=mybible,pg_catalog` بلا `public` fallback؛
   أي جدول ناقص يفشل صراحةً ولا يلمس جدول Ads مشابهًا.
9. حافظ على `MYBIBLE_SESSION_SECRET` ومفاتيح VAPID دون أي تغيير؛ التشغيل على
   Supabase يرفض البدء إذا غاب أي واحد منها.
10. قبل فتح الموقع اختبر session cookie اتعملت على Neon بنفسها بعد التحويل،
    واختبر أن endpoint المفتاح العام لـVAPID يعطي نفس fingerprint.
11. لا تحذف Neon القديمة ولا ترفع عنها read-only. النقل **forward-only بعد فتح
    الكتابة على Supabase**: أي عطل يتصلح على Supabase والموقع يظل في الصيانة
    أثناء الإصلاح. الرجوع لنسخة Neon المجمدة بعد قراءات جديدة يفقد الـdelta
    وممنوع من غير نقل عكسي كامل ومقارنة جديدة.
   تجميدًا جديدًا ونقل delta؛ لا تغيّر الرابط للخلف بشكل أعمى.
