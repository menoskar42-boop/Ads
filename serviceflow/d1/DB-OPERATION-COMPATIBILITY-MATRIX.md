# Service Flow PostgreSQL → D1: operation compatibility matrix

## Scope and evidence

Read-only source audit; no application code, production configuration, Cloudflare
resources, or databases were changed or accessed. Matrix entries group endpoints
only where they share an operation family and transaction boundary; listed
source modules and route families are the operation inventory, not a claim that
every SQL statement has already been rewritten or benchmarked.

Current app architecture: Node/Express on Replit, PostgreSQL `pg` pools, Drizzle
node-postgres for core and CFM storage, and a second maintenance Express app
using `pg` with `search_path=maintenance,public`. D1 is reached through a
Cloudflare Worker binding. **A Worker/API boundary is required** for the
existing Node process to use D1; no Service Flow D1 binding/API currently exists.
Cloudflare documents D1 `batch()` as a sequential transaction which aborts on
statement failure. This differs from a general node-postgres session/lock API.

Legend: **Exact?** means exact behavior is plausible only after the listed
tests; none of the replacements below has been implemented or proven equivalent.

## Background work and database touch schedule

| Job/function and observed trigger | DB operations / current behavior | D1 compatibility and principal risk |
|---|---|---|
| `runDailyAutoBatches` — boot after 30s, each 5-minute tick, manual route, and executor heartbeat; gated by `schedulersEnabled()` for local timers | Uses a Cairo date claim in `app_state`, builds stop/measurement lists from reports, enqueues batches. | Durable unique schedule key + atomic enqueue. Overlap between timer, heartbeat, manual run, or replicas can duplicate batches unless claim and writes are one atomic idempotent operation. |
| `runOneOffMeasure` — same boot/tick/heartbeat triggers | DB marker prevents repeat; on failure marker is deleted and retry is allowed. | Preserve claim/release semantics transactionally; failure must neither strand marker nor duplicate partial batch. |
| `runWfmFetch` — boot/tick/heartbeat; target slots 11:00 and 14:00 Cairo | Checks due slot/state and enqueues whole-site WFM task; in-memory slot plus DB guard. | DB is source of idempotency, not memory. Test restart, overlapping replicas, and slot boundary; duplicate fetch can upload duplicate snapshots. |
| `runPortsMissingSubinfo` / `queueMissingLineDataSubinfo` — boot/tick/heartbeat plus independent 60s wakeup then hourly interval | Scans eligible orders, checks recent queue entries and inserts up to 200 jobs. | Need one scheduler owner, paged scan, uniqueness per line/window, and atomic dedupe. Duplicate jobs or missed lines on partial paging are risks. |
| `runExecFollowups` — executor heartbeat (about every 20s while online) | Transactionally promotes due follow-ups to queue jobs, max 50 each invocation. | Claim/lease + idempotent insert/mark in one batch. Duplicate promotion on overlapping heartbeats is the central risk. |
| `checkAndSnapshot` / `startDailySnapshotScheduler` — boot after 10s, every 15m; only scheduler-enabled instance | At/after configured daily window, writes regularized daily snapshot; catch-up after sleep. | Unique day key and atomic snapshot creation. Duplicate or omitted day snapshot if timer and heartbeat/startup race. |
| `registerCabinetReassign` — starts after 20s; next one-shot timeout follows nearest pending deadline, max 6h; runs even when `SF_SCHEDULERS=off` | Polls one pending-deadline query; processes due rows with row locks; no repeating timer if no pending row. | D1 lease claim and app-level timer/Cron decision. A missed wakeup/restart must be recovered; duplicate processing can corrupt history. |
| `runCableLinker` — startup after 45s, every 30m, plus after imports; process-local `running` guard | Adopts/link pending cable entries to work orders; expires after 7 days; may notify. | Multi-instance idempotency is required; local boolean does not coordinate processes. Duplicate callbacks or mislinked rows are risks. |
| `local-store.ts:runBackfill` — startup after 30s; when viewer opens balance at most every 10m; after stock issue | Backfills technician/work date fields, then stock summaries/notifications read ledger. | Conditional updates and durable dedupe; process-local mutex does not stop another replica. | `QuietSessionStore.maybePrune` — middleware on requests, at most daily, only if DB had a query in last 30s | Deletes expired PG sessions; not a free-running timer. | Keep opportunistic semantics or use expiry cleanup during session reads; avoid a Cron that wakes D1 unnecessarily. Must retain expiry correctness. |
| `ensureSchema` and seed initializers — every process startup | DDL, historical compatibility alterations, some cleanup/seed/sync actions. | Replace with explicit controlled migrations and one-time jobs. Startup DDL/data mutation is not appropriate for a Worker cutover. |

## Recommendation: smallest safe next implementation step

Do **not** start migrating the queue, session store, or scheduled jobs yet.
The smallest useful first implementation, after separate approval, is a
**local-only D1 compatibility test for the read-only CFM centrals lookup**
(`GET /api/cfm/master-data/centrals`) using local fixtures and no production
binding. This tests the Worker/API boundary, authorization handoff, prepared
statement result shape, and response parity without risking data writes. If
the boundary is not acceptable, stop before porting any write route, queue, or
durable session.

The production PostgreSQL database remains untouched and is the rollback
source of truth. Cloudflare docs consulted:

- D1 Worker binding and transactional `batch()`:
  https://developers.cloudflare.com/d1/worker-api/d1-database/
- Supported SQLite SQL/functions:
  https://developers.cloudflare.com/d1/sql-api/sql-statements/
- D1 JSON storage/functions:
  https://developers.cloudflare.com/d1/sql-api/query-json/
