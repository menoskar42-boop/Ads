Project Objective

Develop a new application and service called Oscar Messenger, integrated deeply with the existing Oscar ecosystem, especially Oscar Drive and Oscar Security.

Oscar Messenger should be a standalone messaging application that can operate independently on a user’s mobile phone, while also providing extensive voice-controlled functionality through Oscar Drive.

The goal is to build an Oscar-owned communication ecosystem rather than depending on WhatsApp integration.

The user should be able to communicate with other Oscar Messenger users through internet connectivity, including when they do not have cellular call credit.

1. Oscar Messenger Standalone Application

Oscar Messenger should be a separate application that users can install on their phones.

It must support:

Messaging

* Real-time text messages
* Conversation lists
* Individual chats
* Message timestamps
* Sent, delivered, and read indicators when technically supported
* Reply to specific messages
* Forward messages
* Delete messages
* Basic group conversations
* Message notifications
* Search conversations and messages

Media

* Sending and receiving images
* Sending and receiving videos
* Sending files when practical
* Voice messages
* Playback of voice messages
* Location sharing

Contact Management

* Access the phone’s contacts with user permission
* Display contacts inside Oscar Messenger
* Search contacts manually
* Identify Oscar Messenger users among existing phone contacts
* Allow invitations to contacts who are not Oscar Messenger users
* Avoid uploading the entire contact list unnecessarily
* Respect user privacy and permissions

2. Deep Oscar Drive Integration

Oscar Messenger must be highly compatible with Oscar Drive.

Oscar Drive should be capable of controlling Oscar Messenger through its existing voice-command system.

The user should not need to manually open Oscar Messenger while driving.

Examples:

* “Oscar, send a message to Mahmoud Yacoub.”
* “Oscar, send Mahmoud a message saying I am on my way.”
* “Oscar, send a voice message to my wife.”
* “Oscar, read my latest message.”
* “Oscar, reply to Ahmed.”
* “Oscar, call Mahmoud.”
* “Oscar, send my location to my wife.”
* “Oscar, open my conversation with Mahmoud.”

The commands should work in Arabic and English.

Use the existing Oscar Drive voice system whenever possible.

Do not introduce an AI model or paid AI API for these commands.

Use predefined command patterns, speech recognition, contact matching, and deterministic logic.

⸻

3. Contact Search and Voice Contact Resolution

Oscar Messenger and Oscar Drive must be able to search the user’s existing mobile contacts.

The search should support:

* Arabic names
* English names
* Arabic pronunciation of English names
* English pronunciation of Arabic names
* Full names
* Partial names
* Compound names
* Nicknames and aliases when configured
* Common spelling variations
* Normalization of Arabic text when appropriate

Example:

The user says:

“اتصل بمحمود يعقوب”

or:

“Call Mahmoud Yacoub”

The system searches the phone contacts and identifies the matching person.

If multiple people match, it must ask the user to choose.

Example:

“I found two contacts named Mahmoud. Which one do you mean?”

The user can choose by voice or screen.

The contact resolution system should reuse existing Oscar Drive functionality if available.

Do not create a duplicate contact-search engine unnecessarily.

⸻

4. Voice-Controlled Message Sending

The user must be able to send messages through Oscar Drive without touching the screen.

Example workflow:

User:
“Oscar, send a message to Mahmoud Yacoub.”

Oscar:
“What would you like to say?”

User:
“I am on my way.”

Oscar:
“Send this message to Mahmoud Yacoub: I am on my way?”

User:
“Send.”

Oscar sends the message through Oscar Messenger.

The workflow should also support commands where the complete message is spoken in one command:

“Oscar, send Mahmoud Yacoub a message saying I am on my way.”

Use deterministic voice-command parsing.

Allow configurable confirmation behavior:

* Always confirm before sending
* Confirm only when the contact is ambiguous
* Confirm only when the message was poorly recognized
* Allow direct sending for trusted commands if the user explicitly enables it

Safety and accidental message prevention must be considered.

⸻

5. Voice Messages

The user should be able to create and send voice messages through Oscar Drive.

Example:

“Oscar, send a voice message to Mahmoud.”

Oscar activates recording.

The user speaks.

Oscar stops recording based on the existing interaction design or a predefined stop command.

Oscar sends the recorded audio through Oscar Messenger.

Support commands such as:

* Send voice message
* Stop recording
* Cancel recording
* Send recording
* Record again

Do not create unnecessary AI audio-processing functionality.

⸻

6. Message Reading While Driving

Oscar Drive should be able to announce incoming messages.

Example:

“New message from Mahmoud.”

The user can say:

* “Read it.”
* “Reply.”
* “Send a voice reply.”
* “Call him.”
* “Ignore.”

Allow configurable settings:

* Read messages automatically
* Read only messages from selected contacts
* Do not read messages while driving
* Read messages only when requested
* Privacy mode for sensitive messages

Use the existing speech engine and voice-command infrastructure whenever possible.

7. Oscar Connect, Internet Voice Calls

Oscar Connect should be integrated into Oscar Messenger.

Support internet-based voice calls between Oscar Messenger users.

Requirements:

* Individual voice calls
* Incoming call notifications
* Outgoing calls
* Call acceptance and rejection
* Mute
* Speaker
* End call
* Call history
* Basic connection status

Internet connection is required for both parties.

The user should not need cellular call credit when using Oscar Connect.

Use a suitable established technology such as WebRTC if compatible with the existing architecture.

Do not build a complicated telephony infrastructure unnecessarily.

Video calling is NOT required in the initial MVP.

Keep the architecture extensible for future video calls.

9. Oscar Security Integration

Oscar Messenger must integrate with Oscar Security and Oscar Drive emergency functions.

Emergency SOS

When SOS is triggered:

* Send an emergency notification to configured trusted contacts.
* Include the user’s current location if available.
* Include the last known location if current location cannot be obtained.
* Include the emergency timestamp.
* Provide a direct way for recipients to contact the user.
* Start an Oscar Connect call when appropriate and configured.

Voice Safety Check

Oscar should ask:

“Are you safe?”

The user can answer using predefined commands:

* “I’m safe”
* “I am okay”
* “أنا بخير”
* “إلغاء الطوارئ”
* “Cancel”

The system should recognize configured phrases without requiring an AI model.

If the user confirms safety:

* Stop the emergency escalation process.
* Confirm verbally that the emergency alert has been canceled or resolved.

If the user does not respond:

* Repeat the safety question according to configurable rules.
* Start a countdown.
* Escalate the emergency when the countdown expires.
* Notify trusted contacts.
* Share the current or last known location.

Avoid false emergency cancellations. Allow configurable confirmation for cancellation.

10. Location Sharing

Support:

* Send a one-time location
* Share live location when technically supported
* Share location during an emergency
* Share location during an Oscar Connect call
* Display the timestamp of the last location update
* Clearly indicate when location updates stop

Never display an old location as if it were current.

If connectivity is lost, clearly display the last known location and its timestamp.

* MVP over excessive feature completeness
* Existing code reuse
* Existing infrastructure reuse
* Direct implementation
* Minimal additional files
* Minimal dependencies
* Minimal external services
* No unnecessary AI APIs
* No background jobs unless genuinely necessary
* No Redis
* No microservices
* No unnecessary abstraction layers
* No expensive infrastructure
* No unnecessary autonomous agent workflows

Do not introduce paid services without first explaining:

1. Why the service is required
2. Whether a free alternative exists
3. The expected cost
4. Whether the feature can be postponed
